# 01 整体完整性自查

> 适用：PRD 主流程写完后、需求评审 / 设计评审前第一遍扫。
> 核心：PRD 不是越厚越好，而是这 6 块都讲清。先扫盲点，再决定哪些要落进 PRD。

## 检查清单（6 块骨架）

- **背景 Background**：为什么非做不可？
  - 写清了「问题 + 证据」，而不是「老板要求做 / 为了提升体验 / 参考竞品」
  - 评审读完能判断这件事为什么值得做
- **目标 Goal**：做成什么样算有价值？
  - 目标可量化（如「转化率 18%→22%」），不是「提升用户体验」这种口号
  - 做完后能量化判断是否达成
- **用户流程 Flow**：谁、怎么走、状态怎么变？
  - 角色已定（不同角色流程没混在一张图）
  - 核心路径完整（从进入到完成，每步发生什么）
  - 状态变化已标（每步之后业务状态怎么变，异常分支也标了）
- **业务规则 Rule**：判断逻辑、计算规则、约束
  - 条件和边界值具体（如「满 200 减 30，叠加券不超实付 50%」），不是「按规则算」
  - 研发拿到规则能直接写代码，不用猜
- **异常 Exception**：空状态 / 错误态 / 边界 / 权限
  - 覆盖「如果没数据怎么办 / 校验失败怎么办 / 超范围怎么办 / 没权限怎么办」
- **验收 Acceptance**：怎样算真的做完了？
  - 用 Given-When-Then（如：Given 未登录访问付费页 / When 点购买 / Then 跳登录且原页留存）
  - 研发能当自测清单，你也能当验收尺子

## 收口判断

写到什么程度算「这 6 块都讲清」：每个关键问题在 PRD 里都能找到答案，而不是靠评审来问。背景别只写「老板要求做」、目标别只写「提升体验」、流程别只画主流程、规则别只写「按规则算」、异常别只写正常流程、验收别只写「系统稳定」。
